# Cupboard — Data Model

## Firestore

Current collection:

```text
products
```

Each product uses its barcode as the Firestore document ID.

```text
products/{barcode}
```

## Product document

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| document ID | string | yes | Product barcode |
| name | string | yes for registration | Product name |
| description | string | no | Optional description |
| weight | number | no | Weight in grams |
| portions | number | yes for registration | Current number of portions |
| imageUrl | string | no | Optional product image URL |
| createdAt | timestamp | generated | Creation time |
| updatedAt | timestamp | generated | Last update time |

## Example

```json
{
  "name": "Arroz",
  "description": "Arroz blanco",
  "weight": 500,
  "portions": 4,
  "imageUrl": "https://example.com/arroz.jpg",
  "createdAt": "Firestore Timestamp",
  "updatedAt": "Firestore Timestamp"
}
```

Timestamps are generated by Firestore server timestamps.

## Normalization

services/products.js normalizes Firestore data before returning it to the UI.

The normalized product exposes id, name, description, weight, portions, imageUrl, createdAt, and updatedAt.

Numeric fields are normalized to numbers.

## Product identity

The barcode is the product identity in the current system:

```text
barcode → products/{barcode}
```

Changing a barcode therefore changes document identity rather than simply changing an ordinary field.

## Save behavior

saveProduct(barcode, data) checks whether the document exists.

### Existing barcode

Updates name, description, weight, portions, imageUrl, and updatedAt.

### New barcode

Creates the product fields plus createdAt and updatedAt.

## Portion behavior

updatePortions(barcode, newPortions) stores a value of at least zero.

The current UI changes the quantity by one portion per action.

## Missing data

The normalization layer provides safe defaults for missing fields.

- name → empty string
- description → empty string
- weight → 0
- portions → 0
- imageUrl → empty string
- timestamps → null

## Future model considerations

If Cupboard becomes a shared household application, the model may eventually need user identity, household identity, ownership, locations, units, expiration, movement history, or shopping state.

Do not add these fields preemptively without a product requirement.

## Data-model rule

Keep the product document small until the product actually needs more information.

A simple household inventory should not require a warehouse database model.
